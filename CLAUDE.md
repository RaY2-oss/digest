# Как здесь ориентироваться, не сжигая контекст

Три машины: **VPS** (`yan`, 80.96.59.139, всё публичное), **домашний сервер**
(`bhutyan`, 10.13.13.3, модели и счёт), **рабочий ПК** (`vzad-pc`, Windows).
Связаны AmneziaWG — 10.13.13.0/24.


## Жёсткое правило: домашний адрес не светится в интернете

Распространяется на всё: любой агент, любой ИИ, любой проект, любой скрипт,
любой контейнер на этой машине.

**Наружу — только через VPS `80.96.59.139`. Никаких прямых выходов.**

Домашний публичный адрес — `109.173.45.159`. Он принадлежит не серверу, а
всему жилью: у домашнего сервера своего публичного адреса нет вовсе, только
приватный `192.168.0.104`. Поэтому под лимитом или баном окажутся телефоны,
телевизор и
обычный сёрфинг, а не «какой-то сервис».

Запрещено, даже если так быстрее или меньше капчи:

- метки `fwmark` в mangle, уводящие трафик мимо таблицы `2022` (туннель);
- docker-сети и контейнеры с прямым выходом (`--network host` в обход туннеля,
  свои bridge без маршрута в туннель);
- `ip rule`/`ip route`, ставящие домашний канал раньше туннеля;
- прямые запросы в обход прокси «на один раз, для теста».

Нужно обойти капчу — обходить **отпечатком, а не адресом**: `camoufox`
установлен на обеих машинах и с датацентрового адреса вытаскивает DuckDuckGo
там, где обычный HTTP-запрос получает пустую страницу (замерено 12.08.2026).

Правило проверяется само, а не только записано здесь:

- `egress-guard.timer` — каждые 15 минут опрашивает хост и **каждый**
  запущенный контейнер и сравнивает выходной адрес с ожидаемым;
- при утечке `egress-guard.service` падает, а упавшие юниты сразу видны в
  панели в блоке «Требует внимания»;
- состояние — `/run/egress-guard.json`, логи — `journalctl -u egress-guard`;
- проверить руками: `sudo systemctl start egress-guard.service`.

Почему сторож, а не просто запись: контейнер `sciwriter-searxng` ходил
напрямую через `109.173.45.159`, это было сделано намеренно (капча на
датацентровый ASN) и **описано в README проекта** — и всё равно осталось
незамеченным до замера 12.08.2026. Написанное правило себя не проверяет.

Если прямой выход когда-нибудь действительно понадобится — сначала обсудить с
владельцем, а не включать молча. Откат сплит-туннеля:
`systemctl enable --now sciwriter-splittunnel` (служба оставлена на месте,
выключена из автозапуска).

## Сначала прочитай это, а не обходи файловую систему

**`/opt/panel/inventory.yaml` на VPS** — карта всего: машины, проекты, домены,
зависимости между пайплайнами, где лежат секреты, что известно сломанным.
Один файл вместо `ls /opt`, `systemctl`, `docker ps`, `crontab -l` и чтения
конфигов nginx на двух машинах.

## Живое состояние — одним запросом к агенту, а не серией ssh

На обеих Linux-машинах работает агент `ctl` (порт 9900, токен в
`/etc/ctl/token`). На VPS он слушает только localhost; домашний открыт в VPN
и LAN.

```bash
T=$(cat /etc/ctl/token)                       # на домашнем: sudo -n cat
H=http://127.0.0.1:9900                       # домашний: http://10.13.13.3:9900

curl -s -H "x-ctl-token: $T" $H/facts    # порты, контейнеры, cron, таймеры,
                                         # домены nginx, файрвол, wg — живьём
curl -s -H "x-ctl-token: $T" $H/state    # все службы + метрики хоста
curl -s -H "x-ctl-token: $T" $H/projects # проекты машины + размеры графов
curl -s -H "x-ctl-token: $T" $H/logs/digest-bot?n=200
```

`/facts` отвечает на «что где крутится» без единой ssh-команды и не устаревает:
он собирается по запросу, кэш 60 секунд. **Не переписывай в inventory.yaml то,
что отдаёт `/facts`** — списки портов и cron там намеренно отсутствуют.

## Код проекта — сначала граф, потом файлы

У каждого проекта есть граф от graphify: узлы — функции и файлы, связи —
вызовы и импорты, сообщества — смысловые блоки.

```
<корень-проекта>/graphify-out/graph.json          # сам граф
<корень-проекта>/graphify-out/GRAPH_REPORT.md     # выжимка словами
```

Порядок работы: `GRAPH_REPORT.md` → граф покажет, какие 2-3 файла относятся к
задаче → читать только их. Открывать десяток файлов «чтобы понять структуру»
не нужно, это уже сделано.

Полезные команды (graphify стоит на обеих машинах, `~/.local/bin/graphify`):

```bash
graphify explain "имя_функции"        # что это и с чем связано
graphify path "функция_А" "функция_Б" # как одно достаёт другое
```

Графы пересобирает `graphify-refresh.timer` раз в час, без обращений к LLM.
Руками: `systemctl start graphify-refresh.service`. Лог —
`/var/log/graphify-refresh.log`. Новый проект достаточно дописать в секцию
`projects:` файла `/etc/ctl/units.yaml` — он подхватится сам.

## Чего не делать

- Не останавливать `nginx`, `sshd`, `docker`, `ctl` — потеряешь доступ. В
  `units.yaml` они помечены `controllable: false`, панель их и не предлагает.
- Не трогать `/opt/vpn` на живую: ротация идёт каждые 5 минут, а через тот же
  vhost проходит подписка VPN.
- Не класть секреты в `inventory.yaml` — там только пути к ним.
- `headroom` (vps, 127.0.0.1:8787) — прокси сжатия контекста, через него идут
  запросы к Anthropic и OpenRouter. Останавливать его — значит остановить
  `digest`.
